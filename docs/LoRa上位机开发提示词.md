## 0. 任务

为「DY 电源控制板」开发一个 **LoRa 现场调试上位机**。

用途：现场人员用电脑通过 **LoRa 无线链路**（透传）远程给电源板下发命令、读取状态、查看/修改控制策略。

**已具备的硬件条件**：
- 电脑侧有一个 **USB 转串口 + LoRa 模块**（模块工作在**透传模式**）
- 电源板侧有配对的 LoRa 模块，直连单片机
- 两边**串口参数一致**时，电脑发出的字节会原样出现在板子的串口上，反之亦然
- ⚠️ **上位机不需要关心 LoRa 本身**，只需把它当成一个**普通串口**收发即可

## 4. 协议规格 ★★★ 必须严格遵守

> **核心原则：帧格式一字不改。** 本协议与板子的 RS485 链路**完全一致**，只是物理通道不同。

### 4.1 帧的通用结构

```
┌────────────┬────────┬──────────┬──────────────┬────────────┐
│ 协议头      │ 船号    │ 数据部分   │ CRC16(大端)   │ 帧尾        │
│ ASCII 4~7B │ 1 字节  │ 变长      │ 2 字节        │ "$OVER" 5B │
└────────────┴────────┴──────────┴──────────────┴────────────┘
```

- **船号**：**紧跟协议头之后的 1 个字节**。用于区分**三艘船**（本工程船号 = **`0x01`**）
- **CRC16 覆盖范围**：**从帧首到 CRC 之前**的所有字节（即 `总长 - 7` 字节）
- **CRC16 存放**：**大端**（高字节在前、低字节在后）
- **帧尾**：固定为 ASCII `$OVER`（5 字节）

### 4.2 CRC16 算法（Modbus）

- 多项式：**`0xA001`**（即 Modbus CRC16）
- 初值：**`0xFFFF`**
- 位序：**LSB first**（与下面参考实现一致即可）

**参考实现（JavaScript，直接用）**：

```javascript
function crc16Modbus(bytes) {
  let crc = 0xFFFF;
  for (let i = 0; i < bytes.length; i++) {
    crc ^= bytes[i];
    for (let b = 0; b < 8; b++) {
      if (crc & 1) { crc = (crc >> 1) ^ 0xA001; }
      else         { crc = crc >> 1; }
    }
  }
  return crc & 0xFFFF;
}

// 拼接帧：[头][船号][数据] + CRC(大端) + "$OVER"
function buildFrame(headStr, boat, dataBytes = []) {
  const head = Array.from(new TextEncoder().encode(headStr));
  const body = head.concat([boat], dataBytes);
  const crc  = crc16Modbus(body);
  const tail = Array.from(new TextEncoder().encode('$OVER'));
  return new Uint8Array(body.concat([(crc >> 8) & 0xFF, crc & 0xFF], tail));
}
```

**校验收到的帧**：

```javascript
// 帧总长 len，CRC 位于 [len-7], [len-6]（大端）
const rxCrc   = (bytes[len - 7] << 8) | bytes[len - 6];
const calcCrc = crc16Modbus(bytes.slice(0, len - 7));
const ok = (rxCrc === calcCrc);
```

### 4.3 命令一览

| 命令 | 方向 | 帧长 | 用途 |
|---|---|---|---|
| `$READ` | 下发 | **13** | 读设备状态 |
| `$GETSTR` | 下发 | **15** | 读控制策略 |
| `$STR` | 下发 | **222** | 下发控制策略（35 条规则） |
| `$REST` | 下发 | **13** | 重启板子 ⚠️ |
| `$BDRMC` | 下发 | 变长 | 校时（**纯文本，无 CRC、无船号**） |
| `$ACK` | 上送 | **14** | 命令应答 |
| `$STAR` | 上送 | **30** | 设备状态上报 |
| `$STR` | 上送 | **222** | 控制策略回读 |

### 4.4 `$READ` —— 读设备状态

**发送**（13 字节）：
```
"$READ" + 船号 + CRC16(2B) + "$OVER"
```
**示例（船号 01）**：
```
24 52 45 41 44 01 EB 08 24 4F 56 45 52
```

**接收**：**先回 `$ACK`（14 字节），紧接着回 `$STAR`（30 字节）**，两帧连续到达（共 44 字节）。

**实测响应**：
```
$ACK : 24 41 43 4B 01 01 00 72 68 24 4F 56 45 52
$STAR: 24 53 54 41 52 01 EA 07 09 15 05 02 2B EE 00 03 01 04 01 25 01 04 00 CD 17 24 4F 56 45 52
```

### 4.5 `$GETSTR` —— 读控制策略

**发送**（15 字节）：
```
"$GETSTR" + 船号 + CRC16(2B) + "$OVER"
```
**示例（船号 01）**：
```
24 47 45 54 53 54 52 01 89 E7 24 4F 56 45 52
```

**接收**：`$ACK`（14）+ `$STR`（**222**）。

### 4.6 `$STR` —— 下发控制策略

**发送**（**222 字节**）：
```
"$STR"(4) + 船号(1) + 规则[35][6](210) + CRC16(2B) + "$OVER"(5) = 222
```

**接收**：`$ACK`（14 字节），`error` 字段告诉你是否成功。

> ⚠️ 这是**整表覆盖**：35 条一起发，未使用的条目把"目标设备"填 `0xFF`。

**规则 6 字节格式**：

| 序号 | 字节 | 含义 | 取值 |
|---|---|---|---|
| 0 | 1 | 开始时 | 0–23 |
| 1 | 1 | 开始分 | 0–59 |
| 2 | 1 | 开始秒 | 0–59 |
| 3 | 1 | 工作时长 **低字节** | — |
| 4 | 1 | 工作时长 **高字节** | — |
| 5 | 1 | 目标设备码 | 见 4.9，`0xFF`=本条无效 |

> 工作时长 = **16 位小端无符号整数**，单位**秒**。即 `时长 = byte3 | (byte4 << 8)`。

**实测 `$STR` 帧开头**：
```
24 53 54 52 01 0C 00 00 9C 9F FF 0C 00 00 00 00 FF ...
└─"$STR"─┘ └船号┘ └── 规则0 ──┘ └── 规则1 ──┘
```
规则0：时=12、分=0、秒=0、时长=0x9F9C、目标=0xFF（无效）

### 4.7 `$REST` —— 重启板子 ⚠️

**发送**（13 字节）：
```
"$REST" + 船号 + CRC16(2B) + "$OVER"
```
**示例（船号 01）**：
```
24 52 45 53 54 01 2E A5 24 4F 56 45 52
```
**接收**：`$ACK`（14），随后板子**约 300ms 后复位**。

> ⚠️ **UI 上必须二次确认**，操作不可逆。

### 4.8 `$BDRMC` —— 北斗校时

**这是唯一的纯文本命令**：

```
$BDRMC,YY-MM-DD,HH:mm:ss
```

- **无 CRC、无船号、无 `$OVER`**，直接以 **ASCII 文本**发送
- 年份为 **2 位**（`26` = 2026）
- ⚠️ **时间必须是 UTC**（北京时间 − 8 小时）

**示例（北京时间 2026-09-20 21:02:54 → 发 UTC 13:02:54）**：
```
$BDRMC,26-09-20,13:02:54
```

**接收**：**无应答**。校时成功后，后续 `$STAR` 里的时间会变成正确的本地时间。

> ⚠️ **这是最容易做错的一条**：如果发的是本地时间，板子会再加 8 小时，时间就偏了。

### 4.9 `$ACK` —— 应答帧（14 字节）

| 偏移 | 长度 | 含义 | 示例值 |
|---|---|---|---|
| 0–3 | 4 | 帧头 `$ACK` | `24 41 43 4B` |
| 4 | 1 | 类型：`0`=策略指令，`1`=控制指令 | `01` |
| 5 | 1 | 船只编号 | `01` |
| 6 | 1 | **错误码：`0`=成功，`1`=失败** | `00` |
| 7–8 | 2 | CRC16（大端） | `72 68` |
| 9–13 | 5 | 帧尾 `$OVER` | `24 4F 56 45 52` |

**失败示例**（故意发坏 CRC 时收到）：
```
24 41 43 4B 01 01 01 B3 A8 24 4F 56 45 52
              ↑↑ 错误码 01 = 失败
```

### 4.10 `$STAR` —— 状态上报帧（30 字节）

| 偏移 | 长度 | 含义 | 示例值 |
|---|---|---|---|
| 0–4 | 5 | 帧头 `$STAR` | `24 53 54 41 52` |
| 5 | 1 | 船只编号 | `01` |
| 6–7 | 2 | 年（**小端**） | `EA 07` = 2026 |
| 8 | 1 | 月 | `09` |
| 9 | 1 | 日 | `15` |
| 10 | 1 | 时（本地时间） | `05` |
| 11 | 1 | 分 | `02` |
| 12 | 1 | 秒 | `2B` |
| 13–14 | 2 | 电池电压（小端，**放大 10 倍**） | `EE 00` = 238 → **23.8 V** |
| 15–16 | 2 | NTC1 **环境温度**（小端，放大 10 倍） | `03 01` = 259 → **25.9 ℃** |
| 17–18 | 2 | NTC2 **工控机散热鳍片温度**（放大 10 倍） | `04 01` = 260 → **26.0 ℃** |
| 19–20 | 2 | PCB_NTC **电源板温度**（放大 10 倍） | `25 01` = 293 → **29.3 ℃** |
| 21 | 1 | `sensor_state` 设备状态位（见 4.11） | `04` = 北斗 |
| 22 | 1 | 错误码 | `00` |
| 23–24 | 2 | CRC16（大端） | `CD 17` |
| 25–29 | 5 | 帧尾 `$OVER` | `24 4F 56 45 52` |

> ⚠️ **温度可能为负**：16 位值需按**有符号**解释（例如 `0xFFC0` = −64 → −6.4℃）。

**解析参考**：

```javascript
function parseStar(b) {   // b: 30 字节的 $STAR 帧
  return {
    boat:    b[5],
    year:    b[6] | (b[7] << 8),
    month:   b[8], day: b[9], hour: b[10], minute: b[11], second: b[12],
    voltage: (b[13] | (b[14] << 8)) / 10.0,
    ntc1:    (int16(b[15], b[16])) / 10.0,   // 环境
    ntc2:    (int16(b[17], b[18])) / 10.0,   // 工控机鳍片
    pcb:     (int16(b[19], b[20])) / 10.0,   // 电源板
    sensor:  b[21],
    errcode: b[22],
    crc:     (b[23] << 8) | b[24],
  };
}
function int16(lo, hi) {
  const v = lo | (hi << 8);
  return (v & 0x8000) ? v - 0x10000 : v;   // 有符号解释
}
```

### 4.11 `sensor_state` 位定义

**位为 1 = 该设备上电**：

| 设备 | 位 | 设备 | 位 |
|---|---|---|---|
| 工控机 IPC | `0x80` | 摄像头 CAMERA | `0x08` |
| 声纳 SONAR | `0x40` | 北斗 BD | `0x04` |
| 备用三 BK3 | `0x20` | 备用一 BK1 | `0x02` |
| 雷达 RADAR | `0x10` | 备用二 BK2 | `0x01` |

### 4.12 规则"目标设备码"

| 码值 | 含义 | 码值 | 含义 |
|---|---|---|---|
| `0x00` | 工控机 | `0x05` | 备用一 |
| `0x01` | 雷达 | `0x06` | 备用二 |
| `0x02` | 声纳 | `0x07` | 备用三 |
| `0x03` | 摄像头 | `0x0A` | 工控机+雷达+声纳+摄像头 |
| `0x04` | 北斗 | `0x0B` | 工控机+雷达+摄像头 |
| | | `0x0C` | 工控机+雷达 |
| **`0xFF`** | **本条规则无效** | `0x0D` | 工控机+声纳 |

> `0x08`、`0x09` 未使用，不要发送。

### 4.13 帧接收与切分

**关键**：`$READ` 的响应是 **`$ACK`(14) + `$STAR`(30) 两帧连在一起**，必须能正确切分。

**推荐做法**（比单纯按超时切分可靠）：

1. 持续把串口收到的字节追加到缓冲区
2. 在缓冲区里**按帧头定位**（`$ACK` / `$STAR` / `$STR`）
3. 依据**帧头对应的固定长度**判断是否收齐：
   - `$ACK` → 14 字节
   - `$STAR` → 30 字节
   - `$STR` → 222 字节
4. 收齐后校验 CRC，通过则处理并从缓冲区移除
5. 设置**超时兜底**（如 300ms 无新数据则清空残余缓冲），防止半帧卡死

## 7. 验收标准

| # | 标准 |
|---|---|
| 1 | 能连接 COM 口，参数 9600/8N1 |
| 2 | 点"读设备状态"，能收到并正确解析出**电压、三路温度、8 台设备状态、时间** |
| 3 | 设备状态指示灯与实际 `sensor_state` 位**一一对应** |
| 4 | "读控制策略"能把 35 条规则填进表格 |
| 5 | 修改规则后"下发"，收到 `$ACK` 且 `error=0`；再"读控制策略"能读回相同内容 |
| 6 | "一键校时"后，"读设备状态"的时间与**电脑本地时间一致**（偏差 < 10 秒） |
| 7 | `$REST` 有二次确认，执行后板子重启 |
| 8 | 日志完整记录收发原始字节，可导出 |

## 8. 必须处理的坑点 ⚠️

### 8.1 【最重要】Web Serial 不能在 `file://` 下工作

Web Serial API **要求安全上下文**，直接双击打开 HTML（`file://`）**会失败**。

**必须在 README 里给出解决办法**（二选一）：

**方案 A（推荐）**：附一个启动脚本，用内置 HTTP 服务打开
```bat
:: start.bat  —— 需要电脑上有 Python
@echo off
cd /d "%~dp0"
start "" http://localhost:8000/dy-lora-console.html
python -m http.server 8000
```

**方案 B**：说明用 Chrome/Edge 打开 `chrome://flags` 或命令行参数
```
chrome.exe --allow-file-access-from-files "路径\dy-lora-console.html"
```

> 请在 README 里**把这一步写成最显眼的提示**，否则现场会卡在这里。

### 8.2 必须由用户手势触发

`navigator.serial.requestPort()` **必须在点击事件里调用**，不能在页面加载时自动调用。

### 8.3 两帧连发

`$READ` 的响应是 `$ACK` + `$STAR` **两帧连续**（共 44 字节）。不能按"一次读=一帧"处理，要**按帧头和长度切分**（见 4.13）。

### 8.4 校时用 UTC

见 4.8。发本地时间会导致**偏差 8 小时**。UI 上要明确提示。

### 8.5 温度是有符号数

见 4.10。`int16` 解释，否则负温度会显示成 65500 之类的怪值。

### 8.6 字节序不统一

| 字段 | 字节序 |
|---|---|
| **CRC16** | **大端**（高字节在前） |
| 年份、电压、温度、工作时长 | **小端**（低字节在前） |

### 8.7 `$BDRMC` 例外

唯一一条：**无 CRC、无船号、无 `$OVER`、无应答**。不要套用通用帧格式。

### 8.8 无应答 ≠ 出错

以下情况**设计上就没有应答**，UI 不要报错：
- `$BDRMC` 校时
- 发船号不匹配的帧
- 发未知协议

## 9. 附：可直接发送的示例帧（船号 01）

测试时可直接复制到串口助手验证，也可作为上位机的自测用例：

| 用途 | HEX |
|---|---|
| `$READ` 读状态 | `24 52 45 41 44 01 EB 08 24 4F 56 45 52` |
| `$GETSTR` 读策略 | `24 47 45 54 53 54 52 01 89 E7 24 4F 56 45 52` |
| `$REST` 重启 ⚠️ | `24 52 45 53 54 01 2E A5 24 4F 56 45 52` |
| 船号=02（应无应答） | `24 52 45 41 44 02 EA 48 24 4F 56 45 52` |
| 坏 CRC（应回失败） | `24 52 45 41 44 01 FF FF 24 4F 56 45 52` |

**校时**（ASCII 模式发，注意是 UTC）：
```
$BDRMC,26-09-20,13:02:54
```

**预期响应**（发 `$READ` 后）：
```
$ACK : 24 41 43 4B 01 01 00 72 68 24 4F 56 45 52
$STAR: 24 53 54 41 52 01 EA 07 09 15 05 02 2B EE 00 03 01 04 01 25 01 04 00 CD 17 24 4F 56 45 52
```

## 10. 开发顺序建议

1. **先做串口收发 + 日志**（能把原始字节发出去、收回来并显示 HEX）
2. **再做 CRC + 帧构造/切分**（用第 9 节的示例帧自测）
3. **再做 `$READ` 解析与状态显示**（这是最核心的一步）
4. **然后做 `$GETSTR` / 规则表**
5. **最后做 `$STR` 下发、校时、`$REST`**

每一步都用第 9 节的示例帧验证，避免最后一起调试。
