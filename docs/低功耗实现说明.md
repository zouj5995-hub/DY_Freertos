# DY 电源控制板 低功耗实现说明

| 项 | 内容 |
|---|---|
| 适用固件 | DY_FreeRTOS，2026-09-21 09:23 及以后 |
| 实现方式 | **FreeRTOS tickless idle + CPU SLEEP 模式** |
| 芯片 | STM32F103，主频 72MHz，tick 1ms |
| 生效时间 | **空闲时自动生效，无需应用层做任何事** |

---

## 一、结论速览

**一句话**：让 FreeRTOS 在**没有任务要跑的时候**，把 SysTick 停掉、CPU 进入 **SLEEP** 模式；等下一个任务该醒的时候由中断唤醒，内核自动补偿"睡过去的那段 tick"，所以应用逻辑完全无感。

| 项目 | 改动 |
|---|---|
| 改了哪里 | 只改 `Core/Inc/FreeRTOSConfig.h`，**加 2 个宏** |
| 改了多少 | 净增约 450 字节代码 |
| 应用层要改吗 | **完全不用**，所有任务、延时、超时逻辑照旧 |
| 会丢 485 / LoRa 数据吗 | **不会** |
| 会触发看门狗复位吗 | **不会**（睡眠最长 ~20ms，看门狗超时 4 秒） |

---

## 二、为什么选 SLEEP 而不是 STOP（重要）

需求原本写的是"tickless + STOP"。**但经过对本板的分析，STOP 会直接破坏通信功能**，所以实际实现的是 **SLEEP**。原因如下。

### 2.1 STOP 模式会破坏什么

**STOP 模式会关闭所有时钟（包括外设时钟）**，这在本板上会造成严重后果：

| 受影响的链路 | STOP 下的后果 | 严重程度 |
|---|---|---|
| **USART2（北斗/服务器，9600）** | STOP 下外设时钟停止，**完全无法接收数据** | ❌ 致命 |
| **USART3（工控机，115200）** | 同上，**完全无法接收数据** | ❌ 致命 |
| **LoRa 软串口（PB5 EXTI）** | EXTI 能唤醒，但唤醒后需**重配 PLL 恢复 72MHz**（约 100µs）；而 9600 波特率的位时间只有 **104µs** → **第一个字节必丢** | ❌ 致命 |
| **IWDG 看门狗** | LSI 独立运行，**STOP 下继续计数** → 必须在超时前唤醒 | ⚠️ 需处理 |
| **ADC / GPIO** | 停止工作，醒来需重新初始化 | ⚠️ 需处理 |

> **关键问题**：本板是**被动接收**设备 —— 工控机或服务器**随时可能发命令过来**，而且这个时刻**无法预知**。只要进了 STOP，期间到达的命令就会丢失。所以 STOP 对本板**不适用**。

### 2.2 两种模式对比

| 对比项 | **SLEEP（本次采用）** | STOP（未采用） |
|---|---|---|
| 关闭了什么 | **仅内核时钟** | 内核 + **所有外设**时钟 |
| 外设能否继续工作 | ✅ **能**（USART/ADC/EXTI/IWDG 照常） | ❌ 不能 |
| 唤醒时间 | **< 1µs** | ~10µs（HSI 稳定）+ ~100µs（PLL 锁定） |
| 唤醒后要重配时钟吗 | **不用** | **要**（重跑 `SystemClock_Config()`） |
| 会不会丢 485/LoRa 数据 | **不会** ✅ | **会** ❌ |
| 典型电流（72MHz） | 约 14~20mA | 约 20µA |
| 适用场景 | **需要随时响应通信** | 电池供电、可长时间不通信 |

**所以：用 SLEEP 保住功能，功耗从"满载"降到"待命"，这才是本板的正确取舍。**

## 三、tickless idle 是怎么工作的（原理）

### 3.1 传统 FreeRTOS 的问题

普通 FreeRTOS 每 **1ms** 被 **SysTick 中断**打断一次（因为 `configTICK_RATE_HZ = 1000`）。即使所有任务都在 `vTaskDelay()` 睡觉，CPU 也要每毫秒醒来一次处理 tick —— **纯属空转耗电**。

```
无 tickless：
  任务跑完 ──→ [空闲任务] ─1ms─ [空闲任务] ─1ms─ [空闲任务] ─1ms─→ 下个任务
                 ↑ CPU 全速空转，每 1ms 被中断一次          （72MHz 一直在烧电）
```

### 3.2 tickless 的做法

开启 tickless 后，空闲任务发现"**未来这么长时间内没有任何任务需要运行**"，就会：

1. **停掉 SysTick**（不再每毫秒被中断）
2. **执行 `__WFI()`（Wait For Interrupt）** → CPU 进入 SLEEP，**内核时钟停止**
3. 等待**任意中断**把它叫醒
4. 醒来后，内核根据"实际睡了多久"**补上对应的 tick 数**，任务延时逻辑无缝衔接

```
有 tickless：
  任务跑完 ──→ [查下一个任务还有 18ms] ──→ __WFI() 睡 18ms ──→ [补 18 个 tick] ──→ 下个任务
                                          ↑ 内核停转，几乎不耗电
```

### 3.3 本工程的实际时序

各任务周期（最短决定睡眠上限）：

| 任务 | 周期 |
|---|---|
| TaskComm（通信） | **20ms** ← 最短 |
| TaskPower（供电决策） | 100ms |
| TaskHeartbeat（心跳灯） | 500ms |
| TaskMonitor（采集） | 1000ms |
| TaskWdg（喂狗） | 1000ms |
| TaskSelftest（巡检） | 600000ms（10 分钟） |

因此**每个 20ms 周期内，任务跑完后通常有十几毫秒空闲**，这部分时间 CPU 就可以睡觉。

## 四、本工程的具体实现

### 4.1 改动内容（只改了一个文件）

文件：`Core/Inc/FreeRTOSConfig.h`，在 `/* USER CODE BEGIN Defines */` 区内新增：

```c
/* ===== 低功耗：空闲进入休眠（tickless idle）===== */
#define configUSE_TICKLESS_IDLE                  1
#define configEXPECTED_IDLE_TIME_BEFORE_SLEEP    2
```

**就这两个宏，没有别的地方要改。**

- **`configUSE_TICKLESS_IDLE = 1`**
  启用内核自带的 tickless 机制。本工程用的是 `portable/RVDS/ARM_CM3/port.c`，其 `vPortSuppressTicksAndSleep()` 内部执行 `__dsb(); __wfi(); __isb();`，即**SLEEP 模式**。

- **`configEXPECTED_IDLE_TIME_BEFORE_SLEEP = 2`**
  "只有当预计空闲**至少 2 个 tick（=2ms）**时才值得睡"。设太小会因为频繁进出睡眠而**得不偿失**（进睡眠、醒来的开销超过省下的电），设太大会错过短空闲窗口。2ms 对本工程是合适的。

### 4.2 为什么这样是安全的（三重保障）

**保障一：睡眠时间受"下一个任务何时到期"限制**
内核只会在"预计空闲时间"内睡觉，而这个时间由当前所有任务的延时决定。本工程最短周期是 TaskComm 的 **20ms**，所以**单次睡眠最多约 20ms**。

**保障二：远小于看门狗超时**

| 项 | 值 |
|---|---|
| IWDG 配置 | 预分频 64、重装载 2500 |
| LSI 约 40kHz | 超时 ≈ 64 × 2500 ÷ 40000 ≈ **4 秒** |
| 单次最长睡眠 | 约 **20ms** |
| 余量 | **200 倍** ✅ |

**保障三：HAL 时间基准不依赖 SysTick**
本工程使用 `Core/Src/stm32f1xx_hal_timebase_tim.c`，**HAL 的 `HAL_GetTick()` 由 TIM 中断驱动，不是 SysTick**。所以停掉 SysTick **不会影响任何 `HAL_UART_Transmit(...)` / `HAL_ADC_PollForConversion(...)` 的超时判断**。

> 这一点很关键：很多 STM32 工程把 HAL 时基也放在 SysTick 上，那样开 tickless 会导致 HAL 超时失效。**本工程天然避开了这个坑。**

## 五、效果估算

STM32F103 在 72MHz 下的典型电流（**以数据手册为准**）：

| 模式 | 典型电流 | 说明 |
|---|---|---|
| Run（全速运行，外设全开） | 约 36 mA | 改动前的基本状态 |
| **SLEEP（内核停，外设开）** | **约 14 ~ 20 mA** | 本次启用后空闲时进入 |
| STOP | 约 20 µA | 未采用（见第二节） |
| STANDBY | 约 2 µA | 不适用 |

**实际平均电流取决于"空闲占比"**：

```
平均电流 ≈ 运行电流 × 运行占比 + SLEEP 电流 × 空闲占比
```

本工程任务较密集（最短 20ms 周期），**空闲占比大致在 50%~80%**，因此估算：

| 场景 | 平均电流（估算） |
|---|---|
| 改动前（无 tickless） | 约 **36 mA** |
| 改动后（有 tickless） | 约 **18 ~ 25 mA** |

> ⚠️ 以上为**基于数据手册的估算**，实际值请用**电流表实测**（见第六节）。
> ⚠️ **注意**：本板的供电对象是工控机、雷达、声纳（**10~100W 级**），MCU 省下的这十几毫安对**整机功耗影响不到 1%**。本项优化的价值在于**降低 MCU 发热、提高可靠性**，而不是省总电量。

## 六、如何验证

### 6.1 功能验证（首要）

烧录后按 `docs/现场测试清单.md` 回归，**重点确认通信没受影响**：

| 验证项 | 预期 |
|---|---|
| `$READ` 连续 30 次 | 每次都稳定回 44 字节 |
| `$GETSTR` | 正常回 222 字节 |
| LoRa 发 `$READ` | 正常应答 |
| 规则到点执行 | 时间准确，无漂移 |
| 运行 1 小时 | 无复位（看门狗未误触发） |

**如果出现通信偶发丢帧、或规则执行时间不准**，把 `configUSE_TICKLESS_IDLE` 改回 `0` 即可立即恢复（见 8.2）。

### 6.2 功耗验证

1. 在板子 24V 输入回路串一个**电流表**（或直流电源本身带电流显示）
2. 记录**改动前后**的电流读数对比
3. 更精确的方法：测量 **MCU 的 3.3V 供电支路**电流（串 0.1Ω 采样电阻 + 示波器看波形）

### 6.3 睡眠行为验证（可选）

如需确认 tickless 真的在睡，可以临时在 `vPortSuppressTicksAndSleep()` 里翻转一个空闲 GPIO，用示波器观察（**测完务必删除**）。

## 七、如果将来确实要上 STOP（方案与代价）

如果某天场景变了（比如改成**电池供电**、且**允许长时间不通信**），可以考虑 STOP。做法与代价如下。

### 7.1 实现步骤

**① 覆盖 port 层的弱函数**（`ARM_CM3/port.c` 中该函数是 `__weak`，可自行实现）：

```c
#include "stm32f1xx_hal.h"

void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime);
void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime)
{
    /* 1. 记录睡前 tick */
    TickType_t ulReload = ...;
    /* 2. 用 RTC 或低功耗定时器设置唤醒点 */
    /* 3. 停 SysTick */
    /* 4. 进 STOP */
    HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI);
    /* 5. 唤醒后重配时钟（关键！否则跑在 HSI 8MHz） */
    SystemClock_Config();
    /* 6. 补偿 tick */
}
```

**② 必须解决的配套问题**：

| 问题 | 解决办法 |
|---|---|
| 唤醒后主频降到 HSI 8MHz | 唤醒后**调用 `SystemClock_Config()`** 恢复 72MHz |
| **485/LoRa 通信期不能进 STOP** | 在通信活跃时把最大睡眠时间压到 0（禁止睡眠） |
| **USART 无法唤醒 STOP** | 只能靠 EXTI / RTC，需把通信线接入 EXTI（硬件改动） |
| ADC/GPIO 需重新初始化 | 醒来后重新配置并校准 |

**③ 关键难点**：本板**无法预知何时会收到命令**。要安全进 STOP，必须**把 USART 的 RX 引脚也接到 EXTI**做唤醒源（硬件改板），否则第一个字节必丢。

### 7.2 收益与代价

| | SLEEP（现在） | STOP |
|---|---|---|
| MCU 电流 | ~14–20 mA | ~20 µA |
| 485 通信 | ✅ 完全正常 | ❌ 需改硬件 + 特殊处理 |
| LoRa 通信 | ✅ 完全正常 | ⚠️ 首字节可能丢 |
| 改动量 | **2 个宏** | 覆盖 port 函数 + 时钟恢复 + 硬件改板 |
| 风险 | **低** | **高** |

**结论**：在"随时要收命令"的前提下，**STOP 的代价远大于收益**，所以当前选 SLEEP。

## 八、注意事项

### 8.1 CubeMX 重新生成代码后要检查

`configUSE_TICKLESS_IDLE` 写在 `/* USER CODE BEGIN Defines */` 区内，**CubeMX 会保留**。但重新生成后**务必确认这两个宏还在**。

### 8.2 如何快速关闭低功耗

把下面这行改回 0，重新编译即可（**应用代码一行都不用动**）：

```c
#define configUSE_TICKLESS_IDLE     1   →   0
```

### 8.3 未来的优化空间

如果还想进一步降功耗，按收益排序：

| 优化项 | 预计收益 | 复杂度 | 风险 |
|---|---|---|---|
| **降低主频**（72MHz → 24/36MHz） | 运行电流降 ~40% | 低 | 中断响应变慢，需评估 LoRa 软串口时序 |
| 关闭不用的外设时钟（如 CRC/DMA） | 小 | 低 | 低 |
| 降低 ADC 采样频次（现 1 秒一次） | 小 | 低 | 影响温度保护响应速度 |
| 空闲时切 HSI 8MHz | 中 | 中 | **LoRa 软串口 104µs 位时序可能失准** ⚠️ |

> ⚠️ **特别提醒**：**降低主频或切 HSI 会影响 LoRa 软件串口的位时序精度**（它靠 DWT 微秒延时做位翻转）。如果将来要动主频，**必须先回归测试 LoRa 收发**。

### 8.4 与看门狗的关系

tickless 不影响喂狗逻辑 —— 喂狗是 `TaskWdg` 每 1 秒检查心跳位，而该任务本身会被正常调度唤醒。睡眠最长 20ms 不会导致任何任务"睡过头"。
